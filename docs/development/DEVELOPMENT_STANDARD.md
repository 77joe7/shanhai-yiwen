# 《山海异闻录：天地未定》开发规范

- 状态：受控参考规范
- 适用范围：需求、设计、代码、数据、资源、测试、构建与发布
- 当前平台：桌面浏览器、手机浏览器
- 后续平台：微信小游戏

## 1. 目的与效力

本规范用于保证项目的实现可追踪、可验证、可迁移和可恢复。所有人工开发、AI 辅助开发和自动化修改在开始前均须阅读根目录 `AGENTS.md` 及本规范。

规则优先级如下：

1. 用户在当前任务中的明确指令；
2. 已批准的游戏设计说明书、开发任务书和验收标准；
3. 根目录 `AGENTS.md`；
4. 本规范及平台专项规范；
5. 团队惯例与工具默认行为。

任何偏离规范的做法都必须记录原因、影响、批准人或批准来源、临时措施和恢复日期。不得以“赶进度”为由默许永久例外。

## 2. 产品与平台边界

- 第一阶段以桌面浏览器和手机浏览器可预览、可操作、可验收为目标。
- 后续适配微信小游戏；从首个实现开始隔离平台能力，避免重写业务核心。
- 业务规则、战斗逻辑、数值计算、关卡状态和存档模型应尽量使用与渲染平台无关的纯逻辑实现。
- 平台相关能力至少包括：输入、存储、音频、网络、生命周期、安全区、登录、分享、广告、支付、文件与资源加载。
- 微信登录、支付、广告或分享等尚未批准的能力只能预留接口，不得擅自接入。

## 3. 开发准入条件（Definition of Ready）

开始实现前，任务至少应具备：

- 可追踪的需求来源或任务描述；
- 用户目标、范围和明确的非目标；
- 可验证的验收标准；
- 受影响的平台、模块、数据、存档和文档；
- 已知依赖、风险及兼容性要求；
- UI 任务所需的交互状态、屏幕方向和关键尺寸约束；
- 数据或存档变更所需的 Schema 与迁移策略；
- 无法回退的外部操作所需的明确授权。

信息缺失但不影响产品行为时，可采用最小、可逆且已说明的假设继续；会改变玩法、数据契约、付费逻辑、隐私处理或平台架构时必须先澄清。

## 4. 需求与设计管理

- 游戏设计说明书是当前玩法和产品边界的基线，代码、配置和验收用例必须与其一致。
- 需求应使用稳定编号；代码变更、测试用例和变更日志应能追溯到需求或缺陷。
- 新增系统、改变核心规则、修改跨模块接口、存档结构或平台依赖时，应先形成 ADR，模板见 `ADR_TEMPLATE.md`。
- 发现设计冲突时，应记录冲突位置、影响和可选方案，不得在代码中静默选择一种解释。
- 完成实现时同步更新受影响的说明书、Schema、接口说明、测试和清单。

## 5. 架构与依赖原则

建议逻辑分层为：

1. 核心领域层：玩法规则、状态机、数值与存档模型；
2. 应用层：用例编排、流程控制和对外端口；
3. 平台适配层：Web、移动浏览器和微信小游戏能力实现；
4. 表现层：渲染、界面、动画和输入映射；
5. 基础设施层：网络、资源、日志、构建和遥测。

强制约束：

- 依赖指向稳定的核心层，核心领域层不得反向依赖 DOM、具体渲染器或微信 API。
- 模块通过明确接口交互，禁止跨模块修改内部状态或形成循环依赖。
- 可配置内容与程序逻辑分离；游戏数值、文本、关卡和资源索引不得散落硬编码。
- 全局可变状态应最小化并有唯一所有者；异步流程必须处理取消、超时和重复执行。
- 引入新框架或大型依赖前，记录用途、包体影响、许可证、维护状态、替代方案和微信小游戏兼容性。

## 6. 目录、文件与命名

技术栈建立后，工程至少应清晰区分：

- `src/`：产品源代码；
- `tests/`：自动化测试与测试夹具；
- `assets/`：受控游戏资源；
- `config/` 或等价目录：可验证配置；
- `tools/`：开发与构建工具；
- `docs/`：规范、设计与决策记录；
- `dist/`、`build/` 或等价目录：可再生成且默认不入库的构建产物。

命名应表达用途并保持同类一致。除既有中文受控文档外，代码文件、目录、标识符和资源 ID 优先使用稳定的 ASCII 名称。禁止使用“新建文件”“最终版2”“temp”“misc”等无语义名称。

## 7. 编码规则

- 使用项目统一格式化、静态检查和类型检查工具；工具配置纳入 Git。
- 函数保持单一职责；复杂条件拆分并使用业务语义命名。
- 公共接口、非直观业务约束和临时兼容措施需要注释；注释解释原因，不重复代码表面含义。
- 错误不得静默吞掉；区分用户可恢复错误、业务拒绝和程序缺陷。
- 日志使用结构化类别和级别，不记录令牌、个人信息、完整存档或其他敏感数据。
- 禁止遗留无引用代码、大段注释掉的实现、调试开关、测试后门和无负责人 TODO。
- 时间、随机数和外部 I/O 应可注入或可替换，以支持确定性测试。
- 金额、概率、计时、坐标和容量必须明确单位、范围与精度，避免隐式转换。

具体语言与引擎确定后，应在不降低本规范要求的前提下补充专项规范。

## 8. 游戏数据、配置与存档

- 配置和存档必须具有明确 Schema、版本号、字段类型、必填性、默认值、范围和唯一 ID 规则。
- 数据加载应校验格式、范围、引用完整性和版本；无效数据不得直接进入运行时。
- ID 发布后保持稳定，不复用已删除 ID 表示其他对象。
- 存档通过统一接口读写，业务层不得直接访问 `localStorage`、IndexedDB 或微信存储 API。
- 存档写入采用可恢复策略，避免半写入覆盖唯一有效副本；必要时保留最近一次有效快照。
- Schema 变化必须提供迁移或明确声明不兼容边界，并使用旧版本样本验证。
- 导入数据视为不可信输入，限制大小、结构、内容和解析时间。

## 9. 资源与版权

- 图片、音频、字体、动画和其他资源应登记来源、作者/供应方、许可证、适用范围和修改记录。
- 未确认授权的资源不得进入发布构建；占位资源应清楚标识。
- 资源命名、格式、尺寸、采样率、压缩等级和加载方式应统一并纳入预算。
- 同一资源避免重复拷贝；使用稳定资源 ID 或清单管理引用。
- 构建前检查孤立资源、超预算资源、缺失引用和大小写路径问题。

## 10. Git 版本与备份

`VERSIONING.md` 是详细执行标准，以下条款为不可跳过的质量门禁：

- 开始前检查分支与工作区，保护用户已有修改。
- 每项实质变更更新 `CHANGELOG.md`，按单一目的形成提交。
- 已发布版本使用语义化版本号和带说明的 Git 标签；不得覆盖已发布资产。
- 禁止强制推送共享分支、改写已共享提交或使用破坏性命令处理不明修改。
- 本地提交只提供本机历史，不等同于备份；至少一个受控远程仓库完成推送后才具备异地副本。
- 发布标签必须推送远程；定期验证能从远程克隆并检出标签、读取 LFS/大文件和完成基础构建。
- 远程不可用时可以继续本地、可逆的工作，但交付时必须明确标注“远程备份未完成”及待办动作。
- 禁止将同步盘当作 Git 远程备份。同步冲突可能同时破坏工作区与 `.git`，应另设受控远程。

## 11. 测试与质量门禁

变更应按风险选择下列验证：

- 核心规则：单元测试，覆盖正常、边界、异常和确定性；
- 模块交互：集成测试，覆盖数据流、生命周期和失败恢复；
- 玩家流程：端到端或可复现的手工验收；
- UI：桌面与手机视口、横竖屏、安全区、触控和键鼠验证；
- 数据/存档：Schema 校验、旧版迁移、损坏输入与恢复测试；
- 缺陷修复：先建立可复现条件，修复后增加回归覆盖；
- 构建：至少执行目标 Web 构建和基础启动冒烟测试。

测试失败、构建失败、严重静态检查错误或关键平台流程未验证时不得合并或发布。若检查受环境限制无法运行，必须在交付说明中列出未验证项及风险。

## 12. 性能、稳定性与兼容性

- 性能指标必须以真实目标设备和生产构建测量，不以开发机体验代替。
- 在确定具体引擎和内容规模后，为首屏、可交互时间、帧率、峰值内存、包体、请求数和资源下载量建立量化预算。
- 在量化预算批准前，新增依赖和资源仍需报告体积变化并避免明显的主线程阻塞、重复下载和无界缓存。
- 所有前后台切换、锁屏、来电、页面失焦、网络变化和重复进入流程都应保持状态一致。
- 浏览器支持矩阵、输入和显示要求遵循 `WEB_MOBILE_STANDARD.md`。

## 13. 安全、隐私与内容合规

- 前端与小游戏包均视为公开环境，绝不嵌入服务端密钥或可提升权限的凭证。
- 客户端输入、网络响应、存档和第三方回调都必须校验；关键权限和奖励结果由可信端决定。
- 只收集实现已批准功能所必需的数据，明确用途、保留时间与删除方式。
- 日志、分析和错误报告遵循最小化与脱敏原则。
- 第三方依赖需要锁定版本、核对许可证与已知风险；升级必须经过测试。
- 涉及付费、广告、未成年人、用户生成内容、文化表达或平台政策时，发布前进行专项审核。

## 14. AI 辅助开发规则

- 修改前读取适用规范、需求和代码上下文，并检查 Git 状态。
- 不得臆造不存在的接口、测试结果、产品决策或平台能力。
- 不得覆盖用户修改、擅自清理工作区、扩大任务范围或自动发布外部系统。
- 生成代码必须接受与人工代码相同的审查、测试、安全和版权要求。
- 交付说明必须包括修改范围、验证结果、未验证项、Git 状态和远程备份状态。

## 15. 代码审查与合并

审查至少关注：需求一致性、平台边界、数据兼容、错误处理、安全、性能、测试、文档与 Git 范围。

以下问题阻断合并：

- 改变玩法却无批准需求；
- 破坏存档或接口兼容却无迁移方案；
- 引入密钥、未授权资产或高风险依赖；
- 核心逻辑直接绑定单一平台且无合理记录；
- 必需测试失败，或关键验证结果被虚报；
- 混入无关修改或无法说明来源的生成文件。

## 16. 完成标准（Definition of Done）

任务完成必须同时满足：

- 验收标准逐项满足，且没有未经批准的范围扩张；
- 代码、配置、资源和数据遵循规范；
- 必需测试、构建和目标平台检查通过；
- 受影响的文档、Schema、ADR 和 `CHANGELOG.md` 已同步；
- `git diff` 与 `git status` 已复核，无敏感信息和无关文件；
- 已形成清晰、单一目的的提交；
- 已推送到受控远程，或明确报告仅有本地提交、尚未形成异地备份；
- 交付信息包含变更、验证、风险和后续事项。

## 17. 发布与回滚

- 发布前冻结范围，使用检查表完成目标平台验收。
- 按语义化版本更新 `VERSION` 和 `CHANGELOG.md`，确保文档、构建标识和标签一致。
- 发布构建必须可由受控提交重复生成；记录构建环境、依赖锁文件和必要参数。
- 标签使用 `v主版本.次版本.修订号`，采用带说明标签并推送远程。
- 保留上一可用版本、兼容数据和回滚步骤；数据库、存档或远程配置变更应先验证回滚或前向修复路径。
- 发布后执行启动、核心流程、存档、网络和监控冒烟检查。

## 18. 规范演进

本规范随技术栈和平台目标演进。决定引擎、框架、语言、状态管理、后端和微信小游戏转换方案时，应创建 ADR 并补充对应编码、构建和测试规范。规范修改本身也须更新 `CHANGELOG.md` 并接受 Git 版本管理。
